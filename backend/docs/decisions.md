## 0. 원칙

제출한 세 문서(문제정의서, Product Backlog, 시스템 구조 설계서)는 고치지 않습니다. 대신 아래 원칙으로 구현하고, 차이가 생긴 부분은 이 기록과 발표에서 설명합니다.

1. **구현은 설계서를 그대로 따릅니다.** 설계서에 있는 기능은 명세서에 없더라도 구현합니다. 명세서에 없는 기능을 추가하는 것은 명세 위반이 아니고, 루브릭이 감점하는 것은 범위를 줄이는 경우입니다.
2. **설계서가 정하지 않은 부분은 명세서를 근거로 팀이 정합니다.** 이것을 "설계 구체화"라고 부르며, 설계 변경으로 보지 않습니다.
3. **문서끼리 표기가 다르면 명세서 기준으로 해석합니다.** 문서는 고치지 않고, 어떻게 해석했는지를 기록합니다.
4. 코드 주석과 커밋 메시지에는 근거를 `(D-xx)`로 남깁니다.

| 구분 | 의미 | 항목 수 |
|---|---|---|
| ① 설계 그대로 | 설계서 내용대로 구현 | 설계서 전체 (아래 1장에서 확인이 필요했던 항목만 정리) |
| ② 설계 구체화 | 명세서와 설계서 모두 정하지 않아서 팀이 결정 | 9건 (D-11 ~ D-17, D-25, D-26) |
| ③ 문서 표기 해석 | 제출 문서끼리 표기가 달라 명세서 기준으로 해석 | 4건 (D-21 ~ D-24) |
| 설계 변경 | 설계서와 다르게 구현 | **0건** |

## 1. ① 설계 그대로 — 명세서와 대조해 확인한 항목

명세서에 없거나 명세서보다 범위가 넓지만, 설계서에 있으므로 **그대로 구현**합니다.

| ID | 설계서 내용 | 명세서와의 관계 | 결정 | 스프린트 | 확정 |
|---|---|---|---|---|---|

| D-02 | HttpOnly·Secure 쿠키 + 상태 변경 요청 CSRF 검증 | 명세서는 JWT만 요구 | **구현.** 쿠키로 인증하면 CSRF 방어가 필요함. 쿠키는 `SameSite=Lax`를 함께 적용 | Sprint 1 | ☐ |

| D-21 | Backlog Release Plan | US-06이 "(Should)"로 적혀 있지만 스토리 카드는 Must이고, Sprint 1 Must 합계 27 SP도 US-06을 Must로 계산한 값 | **Must.** 명세서 FR-R-20(본인 예약 내역 조회)이 필수. Release Plan의 "(Should)"는 표기 오류 | ☐ |

## 4. 발표용 요약 (슬라이드 1장)

**제목: 설계 대비 구현 — 문서 정합성 검토 결과**

| 구분 | 건수 | 예시 |
|---|---|---|
| 설계 그대로 구현 | 설계서 전체 | 계층 구조, ERD 8개 엔티티, API, Core Flow 3개 |
| 설계 구체화 (미정 항목 결정) | 9 | 운영 09~22시·60분 단위, 최대 시간은 1건 기준, 체크인 대기 판단식, 노쇼 누적 규칙 |
| 문서 표기 해석 | 4 | US-06 우선순위 표기 오류, FR-R-03 배정, Must 개수 15→14 |
| **설계 변경** | **0** | — |

말할 요점:
1. "구현 중 세 문서를 요구사항 명세서와 대조해서 **불일치 4건, 미정 항목 9건**을 찾았습니다."
2. "제출한 설계서는 바꾸지 않고, 미정 항목만 명세서를 근거로 구체화했습니다. 그래서 설계와 구현의 차이는 0건입니다."
3. "모든 결정은 `docs/decisions.md`에 근거 조항(FR-xx)과 함께 기록했고, 코드에도 `(D-xx)`로 표시했습니다."

예상 질문 대비:
- **"명세서에 없는 퇴실은 왜 넣었나요?"** → 문제정의서 성공 기준과 설계서에 있는 기능이고, 명세서와 충돌하지 않는 추가라서 설계를 따랐습니다(D-01).
- **"최대 4시간을 하루 합계로 보지 않은 이유는?"** → FR-R-03이 "최대 예약 가능 시간"이라고 표현해서 예약 1건 기준으로 해석했습니다(D-12).
- **"잠금 해제는 어떻게 하나요?"** → 명세서와 설계서 모두 정의가 없어 범위 밖으로 두고 제한사항으로 기록했습니다(D-16).
