## 4. AI 오류 대응 사례

> 사소한 오타가 아닌, **요구사항·설계와 어긋난 결과**를 찾은 사례를 우선 기록하세요.
> 좋은 소재 예: FOR UPDATE 누락으로 동시 예약이 2건 성공 / 겹침 조건 경계(`<` vs `<=`) 오류 /
> 정책 값 하드코딩 / `datetime.now()` 직접 호출로 테스트 불가 / 실패 횟수 잠금이 5번째에 걸리는 off-by-one /
> Spring Security 등 다른 스택 기준 답변 / 존재하지 않는 라이브러리 API 제시

### 사례 1 — 1시간 단위 정책인데 분 단위 입력 화면 · 작성자: 조성민 · 관련 US: US-04·05

| 항목 | 내용 |
|---|---|
| 상황 | AI가 생성한 좌석 조회 화면(US-04 초안)에 AI(Claude)로 좌석 클릭 예약 기능을 연결한 뒤 직접 사용 |
| AI 결과 | 시작·종료 시각을 `<input type="time">`으로 분 단위까지 직접 입력하는 화면. 예약 기능을 붙일 때도 AI가 이 입력 방식을 그대로 유지 |
| 문제점 | 운영 정책은 정해진 단위(당시 1시간, 이후 30분)로만 예약 가능(명세서 4.1, D-11). 화면은 아무 분이나 입력할 수 있어 대부분의 입력이 400 `INVALID_TIME_RANGE`가 되고 사용자가 규칙을 알 수 없음 |
| 발견 방법 | **직접 실행** — 화면을 띄워 예약해 보다가 분 단위로 맞춰야 하는 불편을 발견 |
| 해결 과정 | 정책 API(`/api/policies/current`)의 운영 시간·단위를 읽어 시·분을 따로 고르는 드롭다운으로 변경하도록 요청. 지난 시간도 선택은 되지만 "예약할 수 없음" 안내가 나오도록 직접 요구사항을 정함 (`05ee188`) |
| 교훈 | AI는 기능 요구만 보고 UI를 만든다. 정책(단위·운영 시간)을 화면 입력 단계에서 강제하라고 프롬프트에 명시하고, 실제 화면에서 직접 써 보는 검증이 필요 |

### 사례 2 — 조회·예약 시간 규칙 이중화와 예외 경계 오류 · 작성자: 조성민 · 관련 US: US-04·05

| 항목 | 내용 |
|---|---|
| 상황 | 팀원 US-04(좌석 조회) 머지 후, 명세서·합의 규칙 준수 점검을 AI에게 요청 |
| AI 결과 | 조회(`seat_query_service`)와 예약(`reservation_service`)에 시간 검증이 따로 구현되어 있었고, 예약 쪽 검증에 `replace(hour=close_hour)` 사용 |
| 문제점 | ① 종료 24시 정책이면 `replace(hour=24)` → `ValueError` → 500 ② 시간대가 붙은 시각 입력 시 `TypeError` → 500 ③ `slot_minutes=0`이면 0으로 나누기 → 500 ④ 조회는 되는데 예약은 거부되는 구간이 생겨 화면 안내와 실제 결과가 다를 수 있음 (Backlog US-04 AC3) |
| 발견 방법 | 명세 대조 + 경계값 단위 테스트 추가 (자정·24시·시간대 포함 입력·잘못된 정책) |
| 해결 과정 | `booking_rules.py` 한 곳으로 통일(`8039636`). 24시는 자정 기준 분 차이로 비교, 시간대 입력은 400, 잘못된 정책은 503 `OPERATION_POLICY_UNAVAILABLE`(D-27). 조회는 진행 중 시간대를 허용하되 `bookable`/`notice`로 예약 불가를 안내(D-28, `8852f59`). 통일이 Backlog·설계서 위반인지 직접 따져 보고 응답 코드 1개 추가 외 설계 변경 없음을 확인 |
| 교훈 | 같은 규칙을 여러 곳에 두면 경계에서 어긋난다. 규칙은 한 모듈에 두고, AI 코드는 "정상 입력"이 아닌 **경계 입력**으로 테스트해야 한다 |

### 추가 AI 오류 대응 근거 — Refresh와 동시 CSRF 요청

| 항목 | 실제 수행 기록 |
|---|---|
| 상황 | Codex가 생성한 인증 Router의 자동 갱신 동작을 추가 검토 |
| AI 결과와 문제점 | Refresh마다 CSRF까지 새로 발급해, 이전 값을 헤더에 담은 동시 요청이 403으로 실패 |
| 발견 | 회귀 테스트에서 로그인 → 기존 CSRF 저장 → Refresh → 기존 헤더로 로그아웃. 기대 200 / 실제 403으로 실패 재현 |
| 해결 | 로그인 시에는 새 CSRF 발급, Refresh에서는 기존 값을 유지하도록 수정하고 회귀 검증 |
| 교훈 | 토큰 갱신은 여러 탭과 진행 중 요청까지 고려해야 함 |
| 기록 범위 | Codex 수행 기록. 본인 직접 검토·수정·자기평가는 이후 실제 내용으로 추가 |
