# US-01·02·03 인증 구현 및 설명 메모

2026-11-18 · feat/nam · 남준혁 담당 범위. Codex가 구현·자동 검증한 기록이며, 본인의 코드 이해·수정 내용과 최종 AC 승인 여부는 리뷰 후 기입한다.

## 동작과 설계 근거

- `AuthService.signup`: 비밀번호·도메인·중복 검증 → BCrypt 해시 → PENDING 및 인증 정보 저장 → 메일 발송. 동시 가입의 DB UNIQUE 충돌도 학번·이메일 중복 오류로 변환한다.
- `verify_email`: 링크 토큰 또는 이메일+코드 해시 조회 → 회원 잠금 → 현재 시각을 다시 읽고 만료·PENDING 재검사 → ACTIVE·ROLE_STUDENT 전환. 성공 시 다른 인증 수단도 무효화한다 (D-03·15).
- `login`: 회원 행을 잠근 뒤 비밀번호와 실패 횟수를 처리한다. 6번째 실패 시 LOCKED, 잠금 전 성공 시 0으로 초기화한다. 실패 상태를 커밋한 뒤 오류를 반환하여 예외 롤백으로 기록이 사라지지 않게 한다.
- 로그인 성공 시 AuthSession과 Refresh 해시를 저장한다. Router만 HttpOnly·SameSite 쿠키를 설정하며, Refresh 원문은 JSON에 넣지 않는다.
- `refresh`: 세션 잠금 후 폐기·만료 및 현재 계정 상태를 재검사한다. Access를 재발급하되 기존 Refresh 만료를 연장하지 않는다.
- `logout`: 인증 의존성이 확인한 현재 세션 ID를 사용해 revoked_at을 기록하고 쿠키를 삭제한다. 다른 세션은 유지한다.
- `core/deps.py`의 기존 의존성 시그니처는 유지했다. 세션 소유자와 JWT 사용자가 같은지도 검사한다. JWT 필수 클레임과 유형도 검증한다.
- 예약·취소 업무 코드는 변경하지 않았다. 브라우저의 가입·인증·로그인과 공통 API 래퍼·로그아웃 UI를 연결했다.

## 설정과 확인할 제약

- `PUBLIC_BASE_URL`: 인증 링크 주소. 기본 `http://127.0.0.1:8000`.
- `EMAIL_VERIFICATION_EXPIRE_MINUTES=10`, `LOGIN_FAILURE_LIMIT=6`: 인증 설정 파일 값. 예약·노쇼 정책은 기존 OperationPolicy DB를 유지한다.
- `ALLOWED_EMAIL_DOMAIN`: 실제 학교 도메인을 지정해야 학교 이메일만 허용된다. 빈 값이면 도메인 검사를 생략하는 기존 동작이다.
- 메일 실패 시 가입을 롤백한다. 메일 외부 시스템과 DB 커밋은 원자적이지 않으므로, 발송 직후 DB 커밋 실패에 대한 발송 재처리 체계는 이번 범위에 추가하지 않았다.
- 10분 만료 후 인증 정보 재발송 API·화면은 추가하지 않았다. D-15의 재발송 규칙을 구현할 경우 기존 정보를 먼저 무효화해야 한다.
- BCrypt는 UTF-8 72바이트까지 입력을 허용한다. 초과 입력을 잘라 저장하지 않고 `PASSWORD_POLICY`로 안내한다.

## 검증 기록

- 환경: Windows / Python 3.13.14 / 프로젝트 requirements-dev.txt 고정 패키지. 설계서의 Python 3.11에서는 추가 실행 확인이 필요하다.
- `pytest -q -p no:cacheprovider`: **123 passed, 4 skipped**. 건너뛴 4개는 TEST_DATABASE_URL 미설정에 따른 MySQL 통합 테스트이다. 단위 테스트에 pending은 남지 않았다.
- `ruff check .`, `ruff format --check .`, 인증 JS 및 공통 JS의 `node --check` 통과.
- 별도 SQLite·FakeMail 테스트 서버와 임시 Chrome 프로필로 가입 → 코드 인증 → 로그인 → 조회·예약 → 내역·취소 → 만료 Access의 자동 Refresh → 로그아웃 → 6회 실패 잠금을 확인했다. 링크 인증도 확인했고 JS 실행 오류는 없었다. 테스트 전용 서버·메일 조회 경로는 저장소 코드에 추가하지 않았다.
- MySQL 동시 실패 6건·중복 가입 테스트를 추가했다. 이름이 `_test`로 끝나는 DB에서 자체 계정만 정리하도록 했다. Docker 엔진이 실행되지 않아 실제 MySQL 잠금 동작은 미검증이다.
- 실제 학교 SMTP 발송, 실제 학교 도메인 설정, Python 3.11 실행, 팀 전체 공통 파일 리뷰는 남아 있다. SQLite 검증을 MySQL 동시성 검증으로 간주하지 않는다.

## AI 오류 검토 근거

기존 AI 스켈레톤의 `test_us01_wrong_or_expired_code_rejected`는 무작위 코드가 무엇인지 확인하지 않고 `000000`을 오답으로 사용했다. 000000도 발급 가능한 값이므로 유효 코드가 발급된 경우 테스트가 정상 인증을 오류로 판단한다.

발급 코드와 다른 값을 오답으로 선택하도록 수정했고, 생성기를 000000으로 고정한 회귀 테스트에서 이 코드가 정상 인증되는 것을 확인했다. 이 발견·수정·검증은 Codex가 수행했다. 남준혁 본인이 발견·수정한 것으로 기록하지 않으며, 직접 검토한 내용은 이후 별도로 추가한다.

### 추가 오류 대응 — Refresh의 CSRF 변경으로 동시 요청 거부

- 상황: Codex 초안은 Refresh마다 Access와 CSRF 쿠키를 모두 새 값으로 발급했다.
- 문제: 다른 탭이나 이미 준비된 요청이 갱신 전 CSRF 헤더를 보내면 브라우저의 새 쿠키와 달라 403이 발생했다.
- 발견: `test_refresh_preserves_csrf_for_parallel_protected_requests`를 추가하여 로그인 → 기존 CSRF 보관 → Refresh → 기존 헤더로 로그아웃을 실행했다. 수정 전 기대 200 / 실제 403으로 실패했다.
- 해결: 로그인에서는 새 CSRF를 발급하고, Refresh에서는 검증된 기존 CSRF 값을 유지하도록 수정했다. CSRF 검사 자체를 생략하지 않는다.
- 교훈: 인증 쿠키 갱신은 단일 요청뿐 아니라 여러 탭·진행 중 요청에 주는 영향까지 검증해야 한다.
- 수행 주체: Codex가 오류 재현·수정·자동 검증했다. 본인이 직접 발견·수정한 내용으로 제출하지 않고, 본인 리뷰 후 이해·판단 내용을 덧붙인다.
