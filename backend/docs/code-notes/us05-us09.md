## 2. 1분 설명 스크립트 (US-05)

> "예약 생성은 설계서 Core Flow 1을 그대로 구현했습니다.
> 핵심은 **같은 좌석에 동시에 요청이 와도 한 건만 성공**하는 것입니다.
>
> 그래서 한 트랜잭션 안에서 먼저 **회원 행, 그다음 좌석 행을 `SELECT … FOR UPDATE`로 잠급니다.**
> 같은 좌석을 노리는 요청들은 좌석 행 잠금에서 줄을 서게 되고,
> 잠금을 얻은 **뒤에** 겹치는 예약이 있는지 다시 검사합니다.
> 앞 요청이 이미 커밋했다면 그 예약이 보이기 때문에 409를 돌려줍니다.
>
> 잠그기 전에만 검사하면, 검사와 저장 사이에 다른 요청이 끼어들어 둘 다 저장될 수 있습니다.
> 실제로 학생 10명이 동시에 요청하는 통합 테스트에서 1건 성공, 9건 409가 나오는 것을 확인했습니다."

## 3. 1분 설명 스크립트 (US-09)

> "취소는 예약 행을 잠근 뒤 **본인인지, RESERVED인지, 체크인 마감 전인지**를 확인합니다.
> 상태를 CANCELLED로 바꾸는 순간 겹침 검사 대상(RESERVED·CHECKED_IN)에서 빠지기 때문에
> 좌석은 별도 처리 없이 **즉시 가용**이 됩니다(FR-X-04).
> 직접 취소는 노쇼가 아니므로 노쇼 횟수는 건드리지 않고 `penalty_applied=False`로 남깁니다(FR-X-03).
>
> 하나 추가한 규칙이 있는데, **시작 15분이 지나면 취소를 막았습니다(D-26).**
> 노쇼 스케줄러가 10분 주기라서, 그 사이에 취소하면 패널티를 피할 수 있는 빈틈이 있었기 때문입니다."

## 4. 예상 질문과 답

| 질문 | 답 |
|---|---|
| **왜 회원 → 좌석 순서로 잠그나요?** | 모든 요청이 같은 순서로 잠가야 교착 상태(deadlock)가 안 생깁니다. A가 좌석→회원, B가 회원→좌석 순서로 잠그면 서로 상대가 가진 잠금을 기다리며 멈출 수 있습니다. |
| **회원 행은 왜 잠그나요?** | 같은 학생이 다른 좌석을 동시에 예약하는 경우(FR-R-11)를 막기 위해서입니다. 좌석이 달라서 좌석 잠금으로는 직렬화가 안 됩니다. |
| **`(seat_id, start_at)` UNIQUE 제약으로 충분하지 않나요?** | 시작 시각이 다르게 겹치는 경우(10~12시와 11~13시)를 못 막습니다. 설계서 Data Integrity Rules에도 적어 두었습니다. |
| **겹침 조건에 왜 `<=`가 아니라 `<`를 쓰나요?** | 10~12시와 12~14시는 이어지는 예약이라 겹치면 안 됩니다. `<=`를 쓰면 12시 경계가 겹치는 것으로 판정됩니다. 테스트 `test_us05_adjacent_slot_allowed`로 확인합니다. |
| **트랜잭션 격리 수준은?** | READ COMMITTED입니다. 잠금을 얻은 뒤의 조회가 앞 트랜잭션이 커밋한 최신 데이터를 보게 하려고요. MySQL 기본값인 REPEATABLE READ에서는 트랜잭션 처음의 스냅샷을 볼 수 있습니다. (`core/database.py`, `docker-compose.yml`) |
| **SQLite 단위 테스트로 동시성이 검증되나요?** | 안 됩니다. SQLite는 `FOR UPDATE`를 무시합니다. 그래서 동시성은 MySQL 통합 테스트(`test_us05_concurrency.py`)로 따로 검증합니다. |
| **`request_key`는 왜 있나요?** | 버튼을 두 번 누르거나 네트워크 재시도로 같은 요청이 두 번 와도 예약이 하나만 생기게 하려고요. 회원 잠금 뒤에 확인하므로 같은 학생의 중복 요청은 두 번째가 기존 예약을 돌려받습니다. |
| **정책 값(4시간, +7일)은 어디서 오나요?** | `OperationPolicy` 테이블입니다. 명세서 4.1(하드코딩 금지)에 따라 코드에 숫자를 넣지 않았습니다. 시험 기간 모드를 켜면 코드 변경 없이 3시간·다음 날로 바뀝니다. |
| **정책 검증은 Backlog US-05 AC에 없는데요?** | 맞습니다. 명세서 FR-A-20을 기준으로 Sprint 1에 포함했고, 결정 기록 D-25에 근거를 남겼습니다. |
| **취소 시 왜 좌석 상태를 따로 안 바꾸나요?** | 좌석 상태는 저장값이 아니라 예약으로부터 계산하는 값입니다(설계서 Business Rules). 그래서 예약 상태만 바꾸면 됩니다. |
| **타인 예약은 왜 404가 아니라 403인가요?** | 설계서 4장 응답 규칙(403 권한·404 없음)을 따랐습니다. 존재 여부 노출을 줄이려면 404도 가능한 선택지입니다. |
